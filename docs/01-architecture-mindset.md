# 01. アーキテクチャの考え方

コードの前に「なぜこういう形になるのか」を押さえます。
推奨アーキテクチャは決まりごとの集まりではなく、**Android 特有の制約**から導かれた、ごく少数の原則の帰結です。

## 1. 出発点: Android アプリはいつでも殺される

普通のプログラムは `main()` から始まって終わるまで自分で制御できます。Android はそうではありません。

- **部品が勝手に生成・破棄される**: Activity や Fragment は、画面回転・言語変更・マルチウィンドウ化などの「構成変更」のたびに OS が破棄して作り直します。
- **プロセスごと消える**: バックグラウンドに回ったアプリは、メモリが足りなくなれば OS がプロセスを kill します。ユーザーが戻ってきたときは、何事もなかったように復元しなければなりません。
- **入口が複数ある**: 通知、他アプリからの共有、ディープリンク。ユーザーはどこからでも入ってきます。
- **資源が乏しい**: メインスレッドを 16ms 以上止めると画面がカクつきます。重い処理は必ず別スレッドです。

ここから自然に導かれる結論があります。

> **Activity / Fragment に状態やロジックを置いてはいけない。それらは OS の都合でいつ消えるかわからない「入れ物」でしかない。**

Step 0 のレガシーコード([02-refactor-legacy/step0-legacy](../02-refactor-legacy/step0-legacy/src/main/java/com/example/legacytodo/MainActivity.kt))が抱える問題は、ほぼすべてこの原則に反していることから来ています。

## 2. 二つの原則

公式ガイドが掲げる原則は 2 つだけです。あとはすべてこの応用です。

### 原則 1: 関心の分離 (Separation of concerns)

「画面を描く」「データを取ってくる」「業務ルールを適用する」「スレッドを切り替える」は、別々の関心事です。
これらを 1 つのクラスに混ぜると、

- 1 つを変えたいだけなのに他が壊れる
- どこを読めば何がわかるのか見当がつかない
- テストしようにも、画面を起動しないと業務ルールを確かめられない

という状態になります。分けるとは、**各クラスが「自分は何に責任を持ち、何は知らなくていいか」をはっきりさせる**ことです。

### 原則 2: データモデルから UI を駆動する (Drive UI from data models)

UI は「データの現在の姿」を映す鏡であるべきで、UI 自身がデータを持ってはいけません。

- 鏡(UI)は壊れても(Activity が破棄されても)、データが残っていればすぐ描き直せる。
- データが変われば鏡も変わる。「DB は更新したが画面が古いまま」という不整合が起きない。
- データは **永続的なモデル**(DB や Repository が持つもの)が望ましい。プロセスが消えても残るからです。

## 3. 原則から導かれる 3 つの仕組み

### 3-1. 層を分ける

```
┌──────────────────────────────┐
│  UI 層                        │  状態を描く。イベントを上に投げる。
│   UI 要素 (Compose / View)     │
│   状態ホルダー (ViewModel)     │
├──────────────────────────────┤
│  Domain 層 (省略可)            │  複雑な業務ロジック、複数画面で再利用するロジック
│   UseCase                      │
├──────────────────────────────┤
│  Data 層                      │  アプリのデータの「真実」を持ち、公開し、変更する
│   Repository                   │
│   DataSource (Room / API など)  │
└──────────────────────────────┘
依存は上から下へ一方向。下の層は上の層を知らない。
```

関心の分離を「層」という形にしたものです。重要なのは**依存の向き**です。
Data 層は ViewModel を知らず、ViewModel は Compose を知りません。
だから Data 層は UI なしでテストでき、UI 技術を View から Compose に変えても ViewModel は変わりません
([02-refactor-legacy の Step 5](../02-refactor-legacy/docs/step5.md) で実際に体験できます)。

### 3-2. 唯一の信頼できる情報源 (Single Source of Truth, SSOT)

あるデータについて「これが正」と言える場所を 1 か所に決めます。
他の場所にあるものはすべて、そこから派生したコピーです。

- ローカル DB(Room)を SSOT にするのが典型。サーバーから取ったデータも一度 Room に書き、UI は Room だけを見る。
- SSOT だけがそのデータを変更できる。変更したいときは SSOT の持ち主(Repository)に頼む。
- 結果として「同じデータが画面 A と画面 B で食い違う」ことがなくなります。

[01-new-app の OfflineFirstNotesRepository](../01-new-app/app/src/main/java/com/example/archnotes/data/OfflineFirstNotesRepository.kt) がこの形です。

### 3-3. 単方向データフロー (Unidirectional Data Flow, UDF)

状態とイベントの流れる向きを固定します。

```
          状態 (UiState)
   ViewModel ───────────▶ UI
            ◀───────────
          イベント (onClick など)
```

- 状態は**上から下へ**だけ流れる。UI は状態を受け取って描くだけで、自分で書き換えない。
- イベントは**下から上へ**だけ流れる。UI は「ボタンが押された」と伝えるだけで、何が起きるかは決めない。
- 「状態を変える」のは状態ホルダー(ViewModel)だけ。

これを守ると、画面がある見た目になっている理由は「いまの UiState がこうだから」の一点に絞られ、
バグの追跡が「UiState がなぜその値になったか」という一本道になります。

## 4. 典型的な 1 サイクル

「検索語を 1 文字入力した」ときに何が起きるかを、この原則に沿って追うと次のようになります
([01-new-app](../01-new-app/README.md) に実コードでの追い方があります)。

1. UI: `onValueChange` で `viewModel.onQueryChange("k")` を呼ぶ(イベントを上へ)
2. ViewModel: 内部の `query` StateFlow を更新する
3. ViewModel: `query` の変化を受けて UseCase が新しい `Flow<List<Note>>` を返す
4. Data 層: Room の Flow が現在の全件を流す。UseCase がフィルタする
5. ViewModel: `combine` で新しい `NotesUiState` を組み立てる(状態を下へ)
6. UI: `collectAsStateWithLifecycle` が新しい状態を受け取り、再コンポーズする

UI は 1 と 6 にしか関わっていません。「何件に絞られるか」を UI は一切判断していない。これが UDF の実感です。

## 5. アーキテクチャがもたらすもの

- **テスト可能性**: 各層を単独でテストできる。ViewModel のテストは JVM で数ミリ秒で終わる。
- **変更に強い**: データの保存先を変える、UI を Compose にする、といった変更が他の層に波及しない。
- **読みやすさ**: 「業務ルールは UseCase か ViewModel」「SQL は DAO」と決まっているので、探す場所に迷わない。
- **堅牢性**: 構成変更・プロセス再生成・オフラインといった Android の難所を、設計のレベルで吸収している。

逆に言うと、これらが必要ない規模(数画面の使い捨てプロトタイプなど)では、推奨アーキテクチャはやりすぎになることもあります。
「何を得るために何を払うか」は [03-decision-guide.md](03-decision-guide.md) で扱います。

## 6. 一言でまとめると

> Activity は信用しない。状態は ViewModel に、真実は Data 層に置く。状態は下へ、イベントは上へ。
