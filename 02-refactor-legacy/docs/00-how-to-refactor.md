# 00. 既存アプリをリファクタリングする考え方

## 大原則: 「場所を変える」と「仕組みを変える」を同時にやらない

リファクタリングで失敗する典型は、「ついでに Room にして、ついでに Compose にして、ついでに Hilt も」と一度に変えることです。
途中でビルドが通らない期間が長くなり、動かなくなった原因が特定できず、結局 revert することになります。

このリポジトリの各ステップは、**1 ステップ = 1 つの関心事**になっています。

| ステップ | やること | やらないこと |
|---|---|---|
| 1 | DB コードを Activity から Repository へ **移す** | SQL や DB ライブラリは変えない |
| 2 | 状態と業務ロジックを ViewModel へ **移す** | DB の仕組みは変えない |
| 3 | SQLite → Room、List → Flow に **変える** | UI は変えない(MainActivity 無変更) |
| 4 | 手動 DI → Hilt に **変える**、テストを **足す** | ロジックは変えない |
| 5 | XML → Compose に **変える** | ViewModel とテストは変えない |

各ステップの終わりでアプリは同じように動きます。問題が起きたらそのステップだけを疑えばいい。

## なぜこの順番か

### 1. Data 層が最初

- 効果が最も大きい: DB/API 呼び出しは Activity の中で最もかさばり、最もテストしにくい部分。
- UI に影響しない: Activity から見れば「`dbHelper.query(...)` が `repository.getTodos()` になった」だけ。
- 後続のステップの土台: ViewModel を作るとき、Repository があれば ViewModel は Repository を呼ぶだけで済む。

### 2. ViewModel は Data 層の後

- Repository がない状態で ViewModel を作ると、ViewModel に DB コードが移るだけで「Activity の肥大化」が「ViewModel の肥大化」に変わるだけ。
- Repository インターフェースが先にあれば、ViewModel は最初からテスト可能な形で書ける(Step 4 でそれを使う)。

### 3. Room / Flow は ViewModel の後

- Flow の恩恵(「書いたら勝手に流れてくる」)は、受け取る側が ViewModel + StateFlow になっていて初めて活きる。
- Step 2 で「書き込みのたびに `loadTodos()` を呼ぶ」辛さを体験してから Step 3 に進むと、Flow の価値が腹落ちする。

### 4. DI は構造が固まってから

- Hilt は「依存をコンストラクタで受け取る」形になっていないと意味を持たない(入れることはできるが、注入する余地がない)。Step 1〜3 でその形を作っておく。
- 手動 DI(`AppContainer`)を一度挟むと、Hilt が何を自動化しているのかが見える。

### 5. Compose は最後

- UI の刷新は見た目の変化が大きく、リスクも大きい。ViewModel とテストが先にあれば、Compose 化は「同じ UiState を別の方法で描く」作業になり、ロジックの退行をテストで検出できる。
- 逆に、アーキテクチャが整っていない状態で Compose 化すると、Activity にあった混沌が Composable に移るだけになる。

## 実務での進め方

### 小さく始める

アプリ全体を一度に直さない。**1 画面だけ**を Step 1 → 5 まで通し、チームでやり方を合意してから横展開する。
既存の画面と新しい画面は共存できる(同じ Repository を、古い Activity は直接、新しい画面は ViewModel 経由で使う、という期間があってよい)。

### 安全網を先に張る

- 対象画面の主要な操作を手動で確認する手順書(またはスクリーンショット)を用意しておく。
- Repository ができた時点で Fake を書き、ViewModel ができた時点でテストを書く。後続ステップの安全網になる。
- Step 1 の「移すだけ」でも、`withContext` の導入で挙動が変わりうる(エラー時の例外伝播など)。差分は小さくても動作確認は省かない。

### やってはいけないこと

- **既存の DB をいきなり Room に置き換える**: 本番データがある場合、Room は既存テーブルのスキーマを検証して例外を投げる。必ず `Migration` を書くか、別テーブルに移行する。このリポジトリでは各ステップが別アプリなので省略している。
- **ViewModel に Context を渡す**: 文字列リソースが欲しい、Toast を出したい、という誘惑に負けると、ViewModel がテストできなくなる。リソース ID を状態に入れて UI で解決する。
- **Repository を「DAO のラッパー」で終わらせる**: 1 つの DataSource しかなくても、Repository は「将来キャッシュ戦略や複数ソースの責任が集まる場所」として切る。ただし中身が委譲だけなら無理に増やさない。
- **全部の画面を同時に着手する**: コンフリクトとレビュー負荷で止まる。

## このリポジトリでの「同じ動作」の確認方法

各ステップのアプリで次を確認します。

1. 起動時、既存の Todo が表示される(初回は空)
2. テキストを入力して「追加」→ 一覧の先頭に出る、「n 件中 m 件完了」の n が増える
3. 空のまま「追加」→ エラー表示(Toast または Snackbar)
4. チェックを入れる → m が増える。外す → 減る
5. 「削除」→ 一覧から消え、n が減る
6. 画面回転 → 一覧と件数がそのまま(Step 2 以降はちらつきもなくなる)
